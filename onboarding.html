PopPang BE 온보딩 문서

현재 루트 프로젝트를 정적 분석하고, 빌드/테스트 일부를 확인한 결과를 한 문서로 정리했다. 실제 비밀값은 포함하지 않았으며 설정 키와 운영상 주의점만 남겼다.

Java 17 Spring Boot 3.5.6 Gradle 8.14.3 wrapper MySQL Redis Spring Security + JWT SpringDoc OpenAPI

1. 빠른 요약

서비스 성격

PopPang iOS/Android와 웹 화면에 팝업스토어, 찜, 알림 키워드, 추천, 소셜 로그인 API를 제공하는 단일 Spring Boot 서버다.

현재 보안 상태

SecurityConfig가 anyRequest().permitAll() 상태다. JWT 필터는 토큰이 있을 때만 인증 정보를 채운다.

현재 테스트 상태

./gradlew test는 jwt.secret 미설정으로 JwtProvider 생성 중 실패한다.

중요: 설정 파일에 실제 DB, Redis, OAuth, 메일 계정 정보가 포함되어 있다. 이 문서에는 값 자체를 싣지 않았다. 이미 외부에 노출된 적이 있다면 토큰과 비밀번호를 회전해야 한다.

2. 로컬 실행

사전 준비

  • JDK 17
  • MySQL 스키마. 로컬 설정 예시는 poppang_test_db를 바라본다.
  • Redis. refresh token 저장과 팝업 조회수 delta 버퍼에 사용된다.
  • OAuth와 메일 설정. 로컬에서 실제 로그인/가입 메일을 확인하려면 provider별 설정이 필요하다.
  • JWT 설정. 현재 tracked 설정에는 jwt.*가 없어서 테스트 기동이 실패한다.

실행 명령

# Java 버전 확인
java -version

# 로컬 profile로 실행
./gradlew bootRun --args='--spring.profiles.active=local'

# JAR 빌드
./gradlew clean bootJar

# JAR 실행
java -jar build/libs/*.jar --spring.profiles.active=local

# 포맷 적용과 검사
./gradlew spotlessApply
./gradlew spotlessCheck

4. 아키텍처 규칙

Controller->Service->Repository->Entity->DTO/Mapper
  • Controller는 대부분 얇다. request body/path/query를 받고 service를 호출한 뒤 ResponseEntity 또는 ApiResponse를 반환한다.
  • Service 구현체가 트랜잭션과 주요 예외를 담당한다. 도메인 예외는 BaseException(ErrorCode)가 주 패턴이다.
  • 리스트 DTO는 mapper에서 이미지, 추천명, 찜 수, 조회수를 배치 조회한다. 이 패턴은 N+1을 줄이기 위한 핵심 구조다.
  • JPA와 native query가 혼재한다. 지역/구 필터, 거리 계산, 랜덤 조회, 조회수 upsert는 MySQL 의존성이 강하다.
  • 성공 응답 포맷은 아직 통일되어 있지 않다. 웹 API와 token API 일부는 ApiResponse, 앱 API 다수는 raw DTO를 반환한다.
신규 API 작성 시 결정할 것: 같은 도메인의 응답 포맷을 우선 따르되, 장기적으로는 ApiResponse 통일 여부를 팀 기준으로 정해야 한다.

7. 인증과 보안

OAuth 로그인 흐름

Provider token/code->Provider user info->Users.uid upsert->LoginResponseDto
  • Kakao: web은 auth code를 access token으로 교환하고, mobile은 access token을 직접 받는다. Kakao id를 uid로 사용한다.
  • Google: web은 auth code 교환 후 userinfo를 조회하고, mobile은 GoogleIdTokenVerifier로 id_token을 검증한다. sub를 uid로 사용한다.
  • Apple: .p8 키로 client_secret JWT를 생성한 뒤 token endpoint를 호출하고, id_token을 Apple JWKS로 검증한다. sub를 uid로 사용한다.
  • 세 provider 모두 첫 로그인에서 Users를 임시 생성하고, 별도 signup 단계에서 닉네임, 알림 여부, FCM 토큰, 키워드, 추천 카테고리를 채운다.
현재 소셜 로그인과 JWT는 연결되어 있지 않다. LoginResponseDto와 SignupResponseDto에는 access/refresh token이 없다. JWT 발급은 /api/v1/auth/token/test에서만 호출된다.

JWT 구조

  • 서명 알고리즘: HS256
  • Claims: sub=userUuid, iss, iat, exp, typ=ACCESS|REFRESH
  • Access token 만료: jwt.access-token-exp-minutes
  • Refresh token 만료: jwt.refresh-token-exp-days
  • Refresh token Redis key: auth:refresh:{userUuid}
  • 사용자당 refresh token은 1개만 저장된다. 재발급하면 기존 값이 덮어써진다.

Security filter 동작

  • JwtAuthenticationFilter는 Authorization: Bearer ...가 없으면 아무 것도 하지 않고 다음 필터로 넘긴다.
  • 토큰이 있으면 access token인지 검증하고, sub에서 userUuid를 꺼내 UsersRepository.findByUuid로 사용자를 조회한다.
  • 사용자 role은 ROLE_ADMIN 또는 ROLE_MEMBER authority로 변환된다.
  • 토큰 관련 BaseException은 body 없이 HTTP 401만 내려간다.
  • @EnableMethodSecurity는 켜져 있으나 현재 확인된 method 인가는 관리자 V2 비활성화 API 정도다.

보안상 즉시 알아야 할 점

  1. SecurityConfig의 모든 요청이 permitAll()이다.
  2. /api/v1/auth/token/test가 임의 userUuid로 JWT를 발급할 수 있다.
  3. /api/v1/auth/autoLogin은 userUuid만으로 사용자 정보를 반환한다.
  4. 관리자 제보 목록/상태 변경 API에는 method security annotation이 없다.
  5. Users.uid가 provider와 복합 unique가 아니라 단일 unique라 provider 간 uid 충돌 가능성을 배제하지 않는다.
  6. soft-deleted 사용자도 대부분 findByUuid 또는 findByUid 경로에서 배제되지 않는다.

8. Popup 도메인

도메인 역할

Popup 도메인은 팝업스토어 조회, 검색, 지역 필터, 홈/지도 정렬, 회원별 찜 여부, 이미지, 추천 태그, 조회수, 웹 메인용 데이터, 관리자 비활성화, 사용자 제보를 담당한다.

목록 조회 DTO 조립

Popup list->popup ids/uuids 수집->이미지 배치 조회->추천명 배치 조회->찜 수 배치 조회->조회수 배치 조회->DTO
  • PopupResponseDtoMapper는 비회원 DTO를 만든다.
  • PopupUserResponseDtoMapper는 같은 데이터에 isFavorited를 추가한다.
  • 회원 API는 먼저 유저 존재를 확인하고, 유저가 찜한 popup id set을 만든다.

추천 로직

  • 개인화 추천: 사용자의 UserRecommend를 읽고 추천 카테고리별 최대 2개씩 현재 진행 중인 활성 팝업을 모은다.
  • 총 10개가 안 되면 활성 진행 중 팝업에서 랜덤 보충한다.
  • 연관 팝업: 현재 팝업의 PopupRecommend 하나를 찾고, 같은 recommend id의 활성 진행 중 팝업을 가져온다.
  • 연관 팝업 역시 현재 팝업을 제외하고 10개 미만이면 랜덤으로 채운다.

조회수 흐름

POST /view->Redis INCR popup:view:{uuid}:delta->TTL 70s->Scheduler 60s->GETSET 0->MySQL upsert add
  • 스케줄러는 앱 시작 10초 후 최초 실행되고 이후 60초 fixed delay로 동작한다.
  • DB 조회수 API는 Redis에 남아 있는 아직 flush되지 않은 delta를 더하지 않는다.
  • 조회수 DB row가 없는 경우 일부 응답에서 null 처리 여부를 점검해야 한다.

Popup 도메인 주의사항

항목 내용
지도 정렬 enum Swagger 설명에는 NEAREST가 보이지만 실제 MapSortStandard 값은 CLOSEST다.
웹 favorite API /api/v1/web/popup/favorite는 이름과 설명은 찜 기준처럼 보이지만 실제 repository query는 조회수 기준 정렬이다.
숨김 filtered API /api/v1/popup/filtered의 likes/distance 쿼리는 활성 여부와 진행 기간 조건이 없다.
지역/구 목록 주석은 활성 팝업 기준처럼 보이나 실제 SQL에는 is_active = 1 조건이 없고 날짜 조건만 있다.
이미지 upsert 기존 이미지를 전체 삭제하고 새로 저장한다. 부분 수정 API가 아니다.
제보 상태 변경 이미 처리된 제보에 FAVORITE_ALREADY_EXISTS, 제보 id 미존재에 POPUP_NOT_FOUND를 사용해 의미가 어긋난다.
다중 추천 태그 연관 팝업 조회는 findByPopupId의 단일 결과에 의존한다. 한 팝업에 추천 매핑이 여러 개면 예외 가능성이 있다.

9. 사용자 기능 도메인

Users

  • 사용자 식별자는 외부 provider uid인 uid와 내부 API용 uuid가 같이 있다.
  • 닉네임은 unique로 중복 검사 후 변경한다. 다만 service에서 trim한 값을 실제 update에 반영하지 않는 경로가 있다.
  • soft delete는 is_deleted만 true로 바꾸고, hard delete는 row를 삭제한다.
  • 대부분의 도메인 서비스가 findByUuid를 써서 soft-deleted 사용자를 배제하지 않는다.
  • 크론용 API는 is_deleted = 0, is_alerted = 1 사용자와 알림 키워드를 조회한다.

Keyword

  • 알림 키워드는 UserAlertKeyword로 저장된다.
  • 등록 시 사용자 존재는 확인하지만 같은 키워드 중복은 막지 않는다.
  • 조회 API는 repository derived query로 바로 조회하기 때문에 존재하지 않는 userUuid에도 빈 목록을 반환할 수 있다.

Favorite

  • 찜 등록은 userUuid와 popupUuid로 유저/팝업을 조회하고 중복이면 FAVORITE_ALREADY_EXISTS를 던진다.
  • 찜 삭제는 같은 조합을 찾아 삭제하며 없으면 FAVORITE_NOT_FOUND다.
  • 유저 찜 목록은 활성 팝업만 반환하고 회원용 popup DTO mapper를 사용한다.
  • 서비스 중복 검사만 있고 DB unique 제약은 엔티티에 보이지 않아 동시 요청 중복 가능성이 남는다.

Alert

  • UserAlert는 유저가 알림 받은 팝업 이력과 읽음 여부를 저장한다.
  • 등록 시 중복이면 USER_ALERT_ALREADY_EXISTS를 던진다. 컨트롤러 설명의 "중복 요청 시 무시"와 실제 구현이 다르다.
  • 목록은 알림 시간 내림차순이며 활성 팝업만 포함한다.
  • 읽음 처리는 readAt이 null일 때만 현재 시각을 기록한다.

Recommend

  • 전체 추천 카테고리 조회와 웹용 조회는 거의 같은 로직이다.
  • 지도 Featured 추천은 FEATURED_RECOMMEND_IDS = List.of(21)로 하드코딩되어 있다.
  • 사용자 선호 추천은 signup 과정에서 user_recommend에 저장된다.

10. 공통 계층

응답과 예외

파일 역할

Config와 유틸

  • JpaConfig: JPA auditing 활성화.
  • RedisConfig: host, port, password를 읽고 RedisTemplate<String, String>에 string serializer를 설정.
  • SchedulingConfig: 조회수 flush scheduler를 포함한 scheduling 활성화.
  • OpenApiConfig: Swagger title, description, version과 global bearerAuth security scheme 등록.
  • EmailService: Gmail SMTP 465로 가입 알림 메일 발송. 메일 실패는 가입 트랜잭션을 깨지 않도록 catch 후 로그만 남김.
  • StringNormalizer: 지역/구 입력 정규화. 전체와 all은 null로 처리한다.

13. 테스트와 품질

현재 테스트 현황

  • 테스트 파일은 src/test/java/com/poppang/be/PoppangBeApplicationTests.java 하나다.
  • 테스트 내용은 @SpringBootTest contextLoads()뿐이다.
  • Jacoco 같은 커버리지 플러그인은 없다.
  • GitHub Actions는 이슈/PR 자동화와 이메일 알림 중심이며, 빌드/테스트 CI는 확인되지 않는다.

이번 확인 결과

./gradlew test

compileJava              UP-TO-DATE
processResources         UP-TO-DATE
compileTestJava          UP-TO-DATE
test                     FAILED

PoppangBeApplicationTests > contextLoads() FAILED
Caused by: NullPointerException at JwtProvider.java:30

실패 원인은 JwtProvider 생성자에서 props.secret().getBytes(...)를 호출하는데, 현재 테스트 환경에 jwt.secret이 바인딩되지 않아 null이 들어가기 때문이다.

검증을 되살리는 최소 방향

  1. 테스트 profile에 jwt.secret, jwt.access-token-exp-minutes, jwt.refresh-token-exp-days, jwt.issuer를 제공한다.
  2. DB/Redis가 필요한 @SpringBootTest는 Testcontainers 또는 test profile mock 구성을 정한다.
  3. 도메인 단위 service 테스트부터 추가한다. 시작 후보는 favorite, keyword, StringNormalizer다.
  4. CI에서 ./gradlew test와 ./gradlew spotlessCheck를 실행한다.

14. 위험과 개선 후보

높은 우선순위

항목 왜 중요한가 관련 파일
전체 API permitAll JWT 필터가 있어도 토큰 없는 요청을 대부분 허용한다. SecurityConfig.java
테스트 JWT 발급 API /auth/token/test가 임의 userUuid로 토큰을 만들 수 있다. TokenController.java
자동 로그인 userUuid만으로 로그인 응답을 반환한다. AuthController.java, AuthServiceImpl.java
소셜 로그인과 JWT 분리 로그인 성공 후 access/refresh token을 받지 못하므로 JWT 기반 인가 설계와 연결되지 않는다. KakaoAuthServiceImpl.java, GoogleAuthServiceImpl.java, AppleAuthServiceImpl.java
운영 secret 관리 로컬 resources에 실제 secret 파일이 존재한다. JAR/Docker image에 패키징될 수 있다. src/main/resources, Dockerfile, makefile

중간 우선순위

  • 입력 DTO에 @Valid, @NotBlank, @Size 등 검증이 거의 없다.
  • 키워드, 찜, 알림 중복을 DB unique constraint로 보강하지 않았다.
  • assertAccessToken과 assertRefreshToken이 token type 불일치 시 RuntimeException을 던진다.
  • 운영 profile에 ddl-auto: update, show-sql: true, DEBUG 로그가 남아 있다.
  • 마이그레이션 도구(Flyway/Liquibase)가 없다.
  • MySQL native query가 많아 H2 기반 테스트 전환이 쉽지 않다.
  • Apple 설정에는 web-client-id가 있으나 AppleProperties에는 바인딩 필드가 없다.
  • 복구 path /resotre, DTO 이름 UserUpdateFcmTokenResquestDto 등 오타가 실제 API/타입명에 남아 있다.

15. 첫 기여 체크리스트

첫날 읽을 순서

  1. README.md, build.gradle, application.yml로 프로젝트 성격과 실행 방식을 파악한다.
  2. common/response, common/exception, common/security, common/jwt를 읽어 API 공통 규칙을 잡는다.
  3. 가장 단순한 favorite를 Controller - Service - Repository - Entity 순으로 읽는다.
  4. keyword, alert, users로 사용자 기능 흐름을 이어서 본다.
  5. popup은 mapper와 repository native query까지 같이 읽는다.
  6. auth는 provider별 login과 signup이 어떻게 분리되는지, JWT 발급과 왜 연결되지 않는지 확인한다.

새 기능 추가 흐름

  1. 기존 도메인 패키지 구조에 맞춰 presentation, application, infrastructure, entity, dto 위치를 정한다.
  2. 도메인 오류는 ErrorCode에 먼저 추가하고 BaseException으로 던진다.
  3. 읽기 API라면 리스트 응답에서 이미지/추천/찜/조회수 배치 조회가 필요한지 확인한다.
  4. 쓰기 API라면 DB unique constraint와 동시성 중복 가능성을 같이 검토한다.
  5. Swagger 노출 API에는 @Tag, @Operation, 필요한 @Parameter, @Schema를 작성한다.
  6. ./gradlew spotlessApply, ./gradlew test를 실행한다. 현재 test는 JWT 설정 보강 전까지 실패한다.

🗄️ 데이터베이스 스키마 분석

JPA 엔티티 12개 · 리포지토리 쿼리 기반으로 역설계한 PopPang 백엔드 DB 스키마

MySQL 테이블 11개 + Redis 키 2종 스키마 관리 ddl-auto: update 분석일 2026-05-21

이 문서는 onboarding.html의 후속편입니다. 별도 DDL 스크립트가 없는 프로젝트라 JPA 엔티티가 곧 스키마 정의입니다. 엔티티와 리포지토리(네이티브 쿼리 포함)를 도메인별 분석 에이전트로 분해하여 실제 DB 테이블 구조를 복원했습니다.

1스키마 개요

스키마는 application-local.yml의 spring.jpa.hibernate.ddl-auto: update 설정에 따라 애플리케이션 기동 시 엔티티 기준으로 자동 생성/변경됩니다. 즉 SQL DDL 파일이나 Flyway/Liquibase 같은 마이그레이션 도구는 없습니다 — 엔티티 클래스가 유일한 스키마 원본(source of truth)입니다.

ℹ️ auth 도메인엔 테이블이 없습니다

auth 도메인은 JPA 엔티티가 없습니다. 소셜 로그인은 외부 API 호출 + DTO로 처리하고, 리프레시 토큰은 DB가 아닌 Redis에 저장합니다 (17장 참고).

⚠️ 감사 컬럼 적용이 불균일합니다

BaseEntity(created_at/updated_at 자동 기록)를 상속하는 테이블은 5개뿐입니다: users, popup, popup_image, popup_recommend, popup_submission. 나머지 6개 테이블엔 생성/수정 시각 컬럼이 아예 없습니다 — 특히 user_favorite, user_alert, user_recommend 같은 사용자 행동 데이터에 타임스탬프가 없어 "언제 찜했는지" 같은 분석이 불가능합니다. (개선 후보)

2관계도 (ERD)

스키마는 users(회원)와 popup(팝업) 두 개의 허브 테이블을 중심으로, 그 사이를 잇는 조인 테이블들로 구성됩니다.

■ 허브 테이블 ■ 조인/연결 테이블 ■ 종속(1:N) 테이블 ┄┄ 논리적 연결 (DB FK 제약 없음)
user_alert_keyword ──N:1──▶ users user_alert ──N:1──▶ users user_alert ──N:1──▶ popup user_favorite ──N:1──▶ users user_favorite ──N:1──▶ popup user_recommend ──N:1──▶ users user_recommend ──N:1──▶ recommend popup_image ──N:1──▶ popup popup_recommend ──N:1──▶ popup popup_recommend ──N:1──▶ recommend popup_submission ┄┄(submitter_user_uuid ┄┄▶ users.uuid : FK 제약 없음) popup ┄┄(uuid ┄┄▶ popup_total_view_count.popup_uuid : FK 제약 없음)

관계 요약

  • users 1 : N → user_alert_keyword, user_alert, user_favorite, user_recommend
  • popup 1 : N → popup_image, popup_recommend, user_alert, user_favorite
  • recommend 1 : N → popup_recommend, user_recommend
  • M:N 관계는 모두 명시적 조인 엔티티로 풀어냄: 회원↔팝업(user_favorite, user_alert), 회원↔카테고리(user_recommend), 팝업↔카테고리(popup_recommend)
  • 논리적 연결만 존재(JPA @ManyToOne 없이 단순 컬럼): popup_total_view_count.popup_uuid ↔ popup.uuid, popup_submission.submitter_user_uuid ↔ users.uuid
ℹ️ FK 제약은 JPA가 생성

@ManyToOne + @JoinColumn으로 매핑된 관계는 ddl-auto가 실제 FK 제약을 만듭니다. 반면 popup_total_view_count와 popup_submission.submitter_user_uuid는 단순 컬럼이라 DB 레벨 무결성 보장이 없습니다 — 애플리케이션 코드가 정합성을 책임집니다.

테이블 상세 명세

각 컬럼의 SQL 타입은 JPA 어노테이션 + Hibernate 6 / MySQL 기본 매핑 규칙으로 추론한 값입니다. 키 배지: PK 기본키 · FK 외래키 · UQ 유니크 제약.

이 테이블은 다른 테이블과 달리 id 대리키가 없고 popup_uuid가 직접 PK입니다. 조회수는 UPSERT 네이티브 쿼리로 누적됩니다:

INSERT INTO popup_total_view_count (popup_uuid, view_count)
VALUES (:uuid, :delta)
ON DUPLICATE KEY UPDATE view_count = view_count + VALUES(view_count);

ON DUPLICATE KEY UPDATE는 MySQL 전용 문법으로, PK(popup_uuid) 충돌 시 기존 값에 누적합니다. 조회수 누적 흐름은 onboarding.html 9장 참고.

14공통 설계 패턴

① id / uuid 이중 식별자

users·popup·recommend는 내부 PK id(BIGINT)와 외부 노출용 uuid(VARCHAR 36)를 함께 가집니다. FK 조인은 id, API 식별은 uuid. uuid는 @PrePersist로 자동 생성.

② BIGINT IDENTITY 대리키

popup_total_view_count를 제외한 모든 테이블이 id BIGINT AUTO_INCREMENT 대리키를 PK로 사용. popup_total_view_count만 popup_uuid 자연키.

③ 명시적 조인 엔티티

M:N을 @ManyToMany 대신 독립 엔티티로 풀어냄 (user_favorite, user_alert, user_recommend, popup_recommend). 각자 id PK 보유 → 확장 용이.

④ 전부 LAZY @ManyToOne

모든 관계가 단방향 @ManyToOne(fetch = LAZY). @OneToMany 컬렉션 매핑은 쓰지 않음 → 자식은 항상 리포지토리로 직접 조회.

⑤ boolean → BIT(1), is_ 접두사

activated→is_active, alerted→is_alerted, deleted→is_deleted. 필드명과 컬럼명이 다르니 쿼리 작성 시 주의.

⑥ 소프트 삭제 (users 한정)

users.is_deleted 플래그로 소프트 삭제 지원. 단 회원 탈퇴 API는 hard-delete도 별도 제공 — 일관성은 부분적.

18인덱스 / 제약 분석

현재 자동 생성되는 인덱스

  • 모든 테이블의 PK 인덱스 (id 또는 popup_uuid)
  • 유니크 인덱스: users.uid, users.nickname, popup.insta_post_id, recommend.recommend_name
  • FK 인덱스: @JoinColumn 컬럼 10개에 대해 MySQL이 자동 생성 (popup_id, users_id, recommend_id 등)

리포지토리 쿼리로 본 인덱스 추가 후보

네이티브 쿼리들이 다음 컬럼을 반복적으로 필터/정렬에 사용합니다 — 데이터가 늘면 인덱스 추가를 검토할 만합니다:

테이블컬럼근거

🚨 누락된 복합 유니크 제약

조인 테이블들이 "중복 금지" 의도를 애플리케이션 코드(existsBy...)로만 지키고, DB 제약이 없습니다:

  • user_favorite (users_id, popup_id) — 동시 요청 시 중복 찜 가능
  • user_alert (users_id, popup_id) — 중복 알림 이력 가능
  • user_recommend (users_id, recommend_id) — 중복 관심사 가능
  • popup_recommend (popup_id, recommend_id) — 중복 매핑 가능
  • user_alert_keyword (users_id, alert_keyword) — 중복 키워드 가능

→ 각 엔티티에 @Table(uniqueConstraints = @UniqueConstraint(columnNames = {...}))를 추가하면 DB가 직접 막아줍니다. 단 기존 운영 데이터에 이미 중복이 있으면 제약 추가가 실패하므로, 적용 전 중복 정리가 필요합니다.

비효율 쿼리 메모

  • LIKE '%검색어%' (팝업 검색) — 선행 와일드카드라 인덱스 활용 불가. 데이터 증가 시 FULLTEXT 인덱스 검토
  • ORDER BY RAND() (랜덤 팝업) — 인덱스 불가, 전체 정렬. 데이터가 적을 때만 허용 가능
  • SUBSTRING_INDEX(road_address, ' ', 1) 등 함수 가공 컬럼 필터 — 일반 B-tree 인덱스 미적용

19스키마 관점 주의사항

🔴 ddl-auto: update 의존

마이그레이션 도구 없음. 엔티티 수정 = 스키마 변경. update는 컬럼 추가만 반영하고 삭제·타입축소·제약변경은 무시 → 운영 DB와 엔티티가 조용히 어긋날 수 있음.

🔴 복합 유니크 제약 부재

조인 테이블 5종 모두 DB 유니크 제약 없음 (18장). 동시성 상황에서 중복 행 발생 가능.

🟡 uuid에 unique 미선언

users.uuid·popup.uuid는 API 식별자이자 조인 키인데 unique=true가 없음. 값은 UUID.randomUUID()라 사실상 안 겹치지만 제약과 인덱스가 없어 무결성·조회성능 모두 아쉬움.

🟡 감사 컬럼 불균일

6개 테이블에 created_at이 없음. 사용자 행동 테이블 (user_favorite 등)에 시각 정보가 없어 시계열 분석 불가.

🟡 FK 없는 논리적 연결

popup_total_view_count.popup_uuid, popup_submission.submitter_user_uuid는 FK 제약이 없어 고아 데이터(orphan)가 생겨도 DB가 막지 않음.

🟢 boolean이 nullable

is_alerted·is_deleted가 nullable=true. Java boolean 원시형이라 NULL을 못 받지만 DDL은 NULL 허용 → NOT NULL DEFAULT 0이 더 안전.

💡 스키마 개선을 시작한다면

우선순위 제안: ① 조인 테이블 복합 유니크 제약 추가(중복 데이터 정리 후) → ② users.uuid/popup.uuid 유니크 인덱스 → ③ Flyway 도입 후 ddl-auto를 validate로 전환 → ④ 행동 테이블에 created_at 추가. 모두 운영 DB 영향이 있으므로 반드시 팀과 합의하고 진행하세요.
